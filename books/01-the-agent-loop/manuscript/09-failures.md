kind: chapter
title: Failures you can see coming
---

These show up often enough to look for them before the first run. Each one has a symptom you can see in the handback or the trace, and a fix that belongs in the brief.

## The goal is a mood

Symptom: a plausible page, and no way for you to say whether the job is finished.

The loop did what loose language invites. It produced the sound of completion. Rewrite the goal with an output, tests, boundaries, and a stop. If you cannot, the work is not ready to delegate.

## The tool is wider than the job

Symptom: a side effect. A message sent. A file overwritten. A record updated "while it was in there".

The tool list is the job, whether you meant it to be or not. Remove the wide tool. Offer a draft tool instead. If the wide tool must exist for a different job, it should not be available on this one.

## Empty results get filled in

Symptom: smooth paragraphs, specific names and numbers, and no sources. It shows up most around statistics, dates, and citations.

The model has read many briefs. It knows what one sounds like. Sound is not evidence. Require a source line or the word unknown. Treat a filled gap as a failed test, even if the paragraph reads well. Especially if it reads well.

## The loop does not stop

Symptom: searches that change by a word or two, rising cost, and no new facts.

The stop rule is missing, or the check never returns a clear yes. Cap the steps. Cap the cost. Write the condition that counts as done, including "the named sources were checked and the rest is unknown". A loop that can be done will eventually be done. A loop that can only be better will run until something else stops it.

## Memory contradicts the brief

Symptom: an old preference, or a decision from a different customer, shows up in this run. The briefing mentions a product this customer never bought, because the last case file was still in view.

Put the case file and the standing notes on different shelves. Start a run with the brief and an empty case file. Let the loop retrieve archive material only when the brief tells it to, and only for the customer it names.

## The human check trusts the prose

Symptom: you approve because the writing is clear and you are busy. An hour later, a number is wrong.

Fluency is a property of the sentences, not of the facts. Approve against the tests, or do not approve. If the tests take longer than redoing the task, the handback is the thing to fix. Make the sources easier to reopen. Put unknowns at the top, not in an appendix nobody scrolls to.

## A second goal sneaks in

Symptom: you asked for a draft reply. The loop also tries to be maximally helpful. It answers questions the customer did not ask, and it offers a refund the policy does not give.

Extra goals sneak in from default instructions, from a standing note, or from the model's habit of being accommodating. Read the standing instructions. Keep them short. Put the job-specific boundaries where they override the defaults. "Quote the policy. Offer only what section 4 allows. Ask me before you mention money."

Helpful is not a goal. Helpful is an opinion. The brief is the goal.

## Write the failure down as a test

After a bad run, a story in a chat will be forgotten. A test will not.

Every refund amount in a draft must appear in the policy excerpt retrieved for this case. Every customer name in the briefing must match the record id in the source line. If a search returns empty, the section says unknown, and the trace shows the query.

Add the test to the brief before the next run. You are building a small exam from your own mistakes. That exam is worth more than a longer prompt, because a prompt hopes, and a test notices.
